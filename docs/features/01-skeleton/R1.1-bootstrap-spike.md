# R1.1 - the repo bootstrap · built as a spike, not a gated spec

**No spec, no gate, no verifier.** Verified by running the commands, which is the only evidence
that ever mattered for scaffolding.

## Why this is a spike

R1.1 went through four in-harness gate rounds and never converged: 15 → 12 → 11 → 12 blocking
findings. Every one of the ~50 findings was real and inside the closed four-item set - the gate was
not malfunctioning. The mismatch was the artifact.

A spec's four blocking kinds assume requirements describe **behaviour**. The bootstrap's subject is
scaffolding - file contents and exit codes - so there is almost no behaviour to be missing,
contradictory, untestable or edge-cased, and the reader finds those kinds in the **mechanism**
instead. Mechanism is infinitely detailed. Round 4 showed it from the other side: stripping mechanism
cut contradictions from 3 to 1 and doubled edge cases from 3 to 6. The surface moved; it did not
shrink. And each round's fix produced the next round's findings - the anti-vacuity change alone
killed one finding and created three.

`implementation-planner` had already reached this conclusion once, refusing to make Phase 0 a phase
because *"a spike has no requirements for a gate to block on."* The same argument applies here. The
gated pipeline starts at R1.2, where behaviour starts.

`GATE_BYPASS` was considered and rejected: a bypass reviews nothing, and this gate reviewed a great
deal and was right each time. It would have recorded "we skipped review" when the truth was "this
artifact should not have been specced".

The full write-up is in `~/.dotfiles/docs/plan.md` under *Phase 1 evidence*.

## What the gate caught that the build then hit anyway

Worth recording, because it is the argument against dismissing those four rounds as waste. Three
findings from the gate rounds turned up as real build failures within the hour:

| Gate finding | What happened when building |
|---|---|
| `@types/jest` / `@types/node` declared but not in scope, so `tsc` fails over tests using `describe` and `child_process` | Exactly that. 20 errors until `"types": ["node", "jest"]` was added |
| A subpath specifier may carry no type declarations, failing strict typecheck over the fixture | `expo-sqlite/build/SQLiteDatabase` is not in the package's `exports` map. Switched to `expo-sqlite/kv-store`, which is |
| `test-fixtures/` gets linted, and files that reach `expo-sqlite` without using it will fail | Two lint errors. Resolved by ignoring that directory with the reason written in the config |

The gate was reading a config-shaped spec and reporting real problems. It just could not stop.

## What was built

```
package.json app.json tsconfig.json babel.config.js metro.config.js
jest.config.js eslint.config.js .gitignore
lib/guards/    three guards
test-fixtures/ the poison module, its config, and two suites that must fail
```

**The purity boundary, enforced by two different mechanisms.** `jest.config.js` maps
`^expo-sqlite(/.*)?$` - subpaths included, since anchoring on the bare name lets
`expo-sqlite/kv-store` through - to a module that throws on import. Separately, a text scan reads
every tracked source file and fails on any reach outside `lib/db/`. The scan catches spelling, the
poison catches resolution; a file that reaches SQLite through a barrel is caught at the barrel.

**All three guards were proven non-vacuous by breaking them.** That is the part worth keeping:

- Remove the `moduleNameMapper` → both poison tests fail. **And the fixture suite passes**, which is
  stage 1's silent shim reproducing itself in this repo: a suite that imports `expo-sqlite` runs
  green against a no-op returning empty.
- Remove `e2e/` from `testPathIgnorePatterns` → the disjointness guard fails. It has to plant a
  collectable file under `e2e/` to do this, because the directory is empty in this phase and the
  check would otherwise be vacuously true.
- The confinement guard plants a violating file and asserts it is detected, then removes it.
